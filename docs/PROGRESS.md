## Ledger corrections + integrity (12b)

- **Where (simplest choice):** there was no separate ledger page, so the tools sit on the existing **Super Admin–only Fund Settings page** (`/dashboard/settings`, sidebar "Settings") as two new sections at the bottom: **"Fund ledger & corrections"** and **"Integrity check"**. That page is already Super Admin only and is where the fund rules live, so no new menu item or new permission was needed.
- **Corrections never change old rows.** A correction is a **new** ledger entry:
  - **Adjustment** — money in (+) or money out (−), amount, **reason required**.
  - **Reversal** — the **Reverse** button on one entry; adds a new entry with the same amount and the opposite effect, **reason required**. An entry can be reversed **only once** (also a database rule), and a reversal **cannot be reversed**.
  - Before saving, a confirm box shows **amount, balance now and balance after saving**. A correction that would take the fund **below zero is refused**. Only one money entry is saved at a time (same lock as aid payouts).
  - Every correction is in the **Audit Log** ("Fund adjustment" / "Fund entry reversed", with reason and old → new balance).
- **Balance everywhere** (Home, `/fund-report`, dashboard) = the full ledger incl. adjustments and reversals (demo programmers still left out). The Fund Report shows corrections **only as one net total** ("Corrections: +/− ৳ …", only when there are any) — no reasons, no names. The payout check keeps using the whole ledger.
- **"Paid" only with a payout:** an aid case can become *paid* only when its ledger payout entry already exists, inside one database transaction (the normal Pay button does exactly that). Any other code path that tries is stopped with an error; a paid case can never change status again. Same rule for payments: *approved* only together with its ledger entry (the approval now writes the entry first, then the status).
- **Payout limit:** unchanged — a payout can never be more than the balance (MASTER_SPEC §32 says so; nothing in the spec allows otherwise).
- **Integrity check** (read-only, never fixes anything): on the page, and as `php artisan fund:check`. Lists: paid case without payout, payout without case / case not paid, payout ≠ approved amount, approved payment without ledger entry (or different amount), ledger payment entry without approved payment, broken / double reversals, balance mismatch (stored figure vs. adding up every entry), negative balance; as *notes*: a reversed payout / payment whose case / payment still shows paid / approved. **Live result:** 1 problem — the known test case **JPPHAF-AR-2026-0001** (paid by hand, no payout). ## Auth API (3a)

- **Login is by mobile + password** (MASTER_SPEC §16–§17). Phone accepts `01XXXXXXXXX`, `+880…`, `880…`, spaces/dashes — stored as 11 digits (`App\Support\BdPhone`). Email is optional.
- **Sanctum SPA cookie session** (same CSRF flow as 2b: `GET /sanctum/csrf-cookie` → `X-XSRF-TOKEN`). Requests must come from `localhost:3000` (Origin/Referer) to get a session. No API tokens are issued.
- Endpoints (all JSON, messages in bn/en by `Accept-Language`):
  - `POST /api/register` — name, phone, password + password_confirmation (min 8), email?, district (key from `GET /api/districts`), workplace, experience_years (0–60), machines[] and skills[] (1–20 free-text items each; admin-managed lists come in Phase 4). → 201 `{message, data:user}`, status `pending`, **not logged in**. Limit 10/hour/IP.
  - `POST /api/login` — phone, password. Wrong phone/password → 422 `errors.phone`. Correct password but pending/rejected/suspended → **403** `{message, status, rejection_reason}` (status is shown only after a correct password). Approved → 200 `{message, data:user}`; if `data.must_change_password` is true the frontend must go to the change-password screen. Limit **5/minute per phone+IP** → 429 with bn/en message.
  - `POST /api/logout`, `GET /api/me` → `{data:user}`, `POST /api/change-password` (current_password, password + password_confirmation, must differ). Not logged in → 401 "please log in" (bn/en).

## How to run

- **Start:** double-click `start-server.bat` (project root). It starts MySQL (3307), the API (8000) and the website (3000), waits until they answer, then opens http://localhost:3000. The first start can take about a minute. Two small minimized windows appear — "JPPHAF API" and "JPPHAF Frontend". Leave them open while you work. MySQL runs hidden.
- **Stop:** double-click `stop-server.bat`. It closes only JPPHAF's windows/processes, shuts MySQL down cleanly, and shows whether ports 3307, 8000, 3000 are free.
- **Already running?** Running `start-server.bat` again is safe — it says "already running" and just opens the site.
- **"Port XXXX is used by another program - please close it":** another program (for example the Al-Fajr Fashion project's `php artisan serve` on 8000) is using that port. Nothing was started or closed. Stop that other program (or its Laragon/terminal window), then run `start-server.bat` again.
- **Something did not start:** open the minimized "JPPHAF API" or "JPPHAF Frontend" window and read the error; for MySQL see `database/mysql-error.log`.
- Moving the project folder is fine — `start-server.bat` rebuilds `database/my.ini` from `database/my.ini.template` every time.

## Start/stop scripts (0e)

- `start-server.bat` / `stop-server.bat` are batch + PowerShell hybrids (the batch part sets PATH to Laragon's PHP/Node for that window, then runs the PowerShell part of the same file). Works from any folder; paths with spaces/brackets are handled.
- "This project's process" = the process's exe path or command line contains the project folder. Only such processes are treated as "already running" or killed. Anything else on 3307/8000/3000 → warning, nothing touched.
- Missing `backend/vendor` → `composer install`; missing `frontend/node_modules` → `npm install` (run automatically before starting).
- Port 8080 is reserved for Reverb — commented placeholder in `start-server.bat`, nothing started on it yet.
